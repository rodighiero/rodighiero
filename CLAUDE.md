# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
bundle exec jekyll serve   # local dev server (http://localhost:4000)
bundle exec jekyll build   # build to _site/
```

No test suite, no asset pipeline, no npm for the site itself. The home network view consumes a pre-computed similarity graph and layout — when publications change, re-run `KMP_DUPLICATE_LIB_OK=TRUE python3 scripts/build-network.py` to regenerate `_data/network.json` (committed; the script shells out to Node for the layout step, so Node must be on PATH) — it finishes by invoking `scripts/build-cards.py` to layer on the cluster-card text. To only reword the homepage cluster cards (titles/labels), run the fast, model-free `python3 scripts/build-cards.py` alone. See **Network view** below.

`node scripts/spring-easing.js` regenerates the CSS `linear()` spring curves pasted into `_layouts/home.html` (the gallery tiles' transform). It writes nothing — it prints the curves to paste, and exists so a retune is a parameter change rather than a hand-tweaked list of numbers. See **Motion** below.

## Architecture

This is a Jekyll static site — the personal academic website of Dario Rodighiero at `dariorodighiero.com`.

**Content** lives entirely in `_publications/` as Markdown files, one per publication. Each file's front matter drives everything: `title`, `year`, `venue`, `type` (book / chapter / journal / conference / magazine / interview / map), `author`, `doi`, `thumb` (the single image field — the homepage card + social-preview image; optional `img_border: true` draws a hairline around the card). Optional bibliographic fields enrich the formatted citation (and the homepage search index) without appearing in the visible meta line: `editor`, `translator`, `publisher`, `place`, `volume`, `issue`, `pages`. Two more are invisible everywhere but the metadata — `issn` and `isbn`, which exist purely for Google Scholar and Zotero (see **SEO**); write the ISSN-L (normally the print one) when a journal has both, and note the check digit may be an X (`0024-094X`). The `editor`/`translator` byline contributors are joined by `preface` (a preface/foreword author who is not a co-author): it renders in the byline as "Preface by …" (via `byline-text.html` / `byline-home.html`) and is added to the search index. The `interview` type adds one more byline contributor, `interviewer` (the person who conducted an interview — Chicago cites interviews under the interviewee, so Dario stays the `author` and the interviewer renders as "Interview by …", homepage "interview with / interview by …"); like `preface` it is searchable. Note `venue` is type-dependent (for a book chapter `venue` is the **book title** and the press goes in `publisher`; for a book or a map `venue` *is* the press) — which is why the type table says how to read it (`container`, see below). The `type` taxonomy is defined once in `_data/publication_types.yml` (label, Schema.org type, DC.type, citation meta tag, `container`) — adding a new type means adding one entry there. The `layout: publication` is set globally via `defaults:` in `_config.yml`, so individual files do not declare it.

The body of each file is the abstract. Full-text articles (the complete published text, not just an abstract) put the lead/abstract paragraph first, then a `<!--more-->` marker, then the full text using `##` for section headings. The layout italicizes the part before `<!--more-->` as the lead. Footnotes/references inside full-text articles use kramdown footnote syntax (`[^1]` … `[^1]:`) and follow **Chicago author-date** style (e.g. `Author, First. Year. *Title*. Place: Publisher.`). Figures use `{% include figure-single.html %}`; **tables** wrap a Markdown table in `<figure class="data-table" markdown="1"> … <figcaption>Table N. …</figcaption> </figure>` (the `markdown="1"` opts the inner table into kramdown parsing, and the `figure`/`figcaption` styling is inherited; column alignment is set per column in the Markdown header, e.g. `|:--|--:|`). Table styling lives in `_layouts/publication.html` under `.body figure.data-table`. The figure width modifiers double up for both images and tables: `narrow` (33%) / `half` (50%) / `three-quarter` (75%) shrink (e.g. `class="data-table half"` shrinks a table to its content width), and `wide` breaks out to ~990px (centered, wider than the 660px text column) — useful for wide many-column tables such as `class="data-table wide"`. `full` is image-only.

**Quotation marks**: use curly quotes (`“ ”`), never caporali/guillemets (`« »`), for Italian and English text. The only exception is French-language quotations, which keep French guillemets.

**CSS** is fully inlined (no external stylesheets, to avoid render-blocking requests): `_includes/styles-base.css` holds the shared foundation (design tokens in `:root` — type scale, line heights, light/dark colors — plus base typography, `.card-meta`, `.authors`, `.cite-ref-btn`, and the mode toggle) and `_includes/styles-font.css` the `@font-face` rules; both layouts `{% include %}` them at the top of their page-specific `<style>` block. (`fonts/nunito.css` still exists only for the standalone `404.html`.) JS is inlined in the layouts; shared snippets live in `_includes/site-scripts.html` (mode toggle, cite buttons) and `_includes/site-head.html` (everything both `<head>`s share verbatim: the pre-paint color-scheme restore plus the page-invariant meta/link tags — viewport, robots, author, theme-color, `og:site_name`, `twitter:card`, the RSS link, the Dublin Core schema links and the icon/manifest set). No build step:
- `_layouts/home.html` — the only top-level publications page. Two view modes, toggled in the search bar and persisted in `localStorage` under `publicationView`: a **gallery** (custom JS masonry — newest first, packed by shortest column; the column count and the page's own width both follow from one fixed card width, see **Gallery grid** below) and a **network** (publication similarity graph — see **Network view** below). (A third **list** view was removed; cards no longer carry an abstract/`.card-desc` at all.) A single full-width search bar filters across title, authors, editor, translator, venue, publisher, year, type label, volume, issue, pages, DOI and language; in network view it fades non-matching nodes and edges (and links touching them) instead of hiding them. Alongside free-text search there is a **publication-type filter** (`activeType`): each card carries `data-type="{{ type }}"`, and setting a type (via an action card or the `?type=<type>` URL param) restricts the gallery to that type and fades the rest in network view, reusing the same `applySearch` pipeline. Both filters are shareable in the URL (`?q=`, `?type=`, `?view=`) and cleared together by Escape or by clicking the active view button. Language is searchable by name (`english`, or `french`/`français`/`francais`, or `italian`/`italiano`) — derived per card from the front-matter `lang` (absent = English) and appended to each card's `data-search` haystack; only distinctive full names are indexed (not the 2-letter ISO codes, which as substrings would match unrelated words). Author/editor/translator/preface lines come from `_includes/byline-home.html`, which strips "Rodighiero" and prefixes with `with` / `edited with` / `translated with` / `preface with` (or `edited by` / `translated by` / `preface by` when Dario is not in the list). **Gallery grid**: the card width is the constant and the column count follows from it, rather than a set of hand-picked breakpoints. `--card-w` (270px) and `--card-gap` (24px) are declared once in `styles-base.css` and read at runtime by the masonry (`CARD_W`/`GAP_X`, via `getComputedStyle`) instead of being copied into it, so retuning a card is a one-place edit that the header's alignment picks up on its own. The gallery fits as many `--card-w` columns as the page can hold, capped at 4, so a card is the same size at every width above mobile and the leftover goes to the margins — and `syncPageWidth()` then sizes `document.body` to exactly what the current count spans (the counts change at 612 / 906 / 1200 px), so the header, bio, search bar and footer all end where the last card ends rather than a 2- or 3-column grid sitting centred in a wider page. It measures `document.documentElement.clientWidth`, **not** `window.innerWidth`: the latter counts a classic scrollbar (Windows, Linux, macOS set to always show them) as page width, and the grid would then overhang the body by exactly the scrollbar's width — a horizontal scrollbar on the whole page. Below two columns there is no grid left to speak of: one full-width column, which is the mobile layout — but the vertical gap between stacked tiles stays `CARD_W / 4`, a quarter of a *card* and not of that full-width column, which would make the gap itself the size of a card. **Everything else on the page is laid out on those same columns**, so the whole page is one grid rather than a grid with a header and a footer beside it. The header uses `repeat(auto-fill, minmax(min(var(--card-w), 100%), 1fr))` with `var(--card-gap)`, each column padded by the `--card-pad` a card pads its own content with: because the body is sized to the grid, it takes exactly as many columns as the gallery below it, so column 2's left edge lands on card 2's left edge and not merely on the row's outer end, and the bio paragraphs wrap onto a second row as the count drops instead of the header collapsing to one full-width column (which used to set 12px text on an 858px measure the moment the 4th column stopped fitting). The `minmax(min(…), 1fr)` form is what keeps a viewport narrower than a single card from overflowing; where the body *is* grid-sized, `1fr` resolves to `--card-w` exactly. The footer and the network view follow the count instead of hardcoding four: `syncPageWidth` publishes it as **`--cols`** (the number to compute with) and **`data-cols`** (the hook for rules that can't, since a grid line counted from the end needs a line to exist) on `<body>`, and both use `repeat(var(--cols), 1fr)` with `var(--card-gap)` — which reproduces a card's width exactly. The footer's quote takes the last two columns of four or three, the last of two, and the whole row at one (`data-cols`); the network's sidebar is one column and its stage the rest, so the panel is exactly a card wide and the stage starts on a card edge. The CSS carries `body { --cols: 4 }` for the moment before the masonry first runs (which is before the first paint) and for a reader with no JS. The **905px** boundary — where the grid drops from 3 columns to 2 — is where the view toggle, the filter count and the special cards are hidden and the network view is forced back to gallery; the JS asks for it as `matchMedia('(max-width: 905px)')`, the identical test the CSS runs, since a media query is matched against the viewport without its scrollbar while `innerWidth` includes one, and in the band between those two answers the toggle would be hidden with the network view still live — a reader with it persisted, in a view with no visible way out. One consequence to keep in mind when touching `setView`: `syncPageWidth()` is called from `layoutMasonry()`, which the network branch must not run, so that branch syncs the width itself before the graph is fitted into the stage (a page opening straight into `?view=network` would otherwise keep the stylesheet's 4-column cap), and `networkApi.refit()` (a scale and a translate, no simulation) covers the stage-size changes the graph's own listener cannot see, since that one ignores every resize arriving while the network is not the view on screen: a page-width change with no window resize behind it, and — called on the way into the view — every window resize that happened while the gallery was showing, which would otherwise meet the reader with a graph still scaled to the stage it last saw. **Special cards**: the gallery flow can also hold non-publication tiles (class `.action` for a one-off view/type/search trigger, or `.filter` for a cluster tile that sets a persistent filter — both distinct from `.publication` so the count/search/network-clone logic ignores them). They come from `_data/home_cards.yml`: a list of manual **action cards** (`label`, `action`, optional `year`/`eyebrow`/`venue`/`sublabel`) whose `action` is `view:<gallery|network>` (switch view), `type:<publication-type>` (type filter), or `search:<terms>` (free-text query); an optional `pin: first` renders the card as the leading gallery tile (before the forthcoming works). **Auto research-cluster cards** are a second, generated source: one card per `site.data.network.clusters` entry (see **Network view**), each carrying its member slugs in `data-slugs` and a `cluster:<id>` action, interleaved into the year-sorted flow at the **midpoint of its span** (just before the publication named by the cluster's `anchor_slug`), so the cards spread through the timeline rather than clumping. Like the `view:network` card, it reads as a **short title over a quieter description** — the cluster's emitted `title` in the `.card-title` slot and its `description` in the `.card-text` slot beneath, the same place — and, via the shared `.authors, .card-text` rule in `styles-base.css`, the same typography — a publication card gives its authors. Its meta line reads `Research cluster <n>`, numbered by the order the cards are emitted down the gallery (the `_cluster_n` counter in `home.html`), not by the cluster's internal `id`. Publication tiles and plain action tiles are **one card style**: both carry a shared `.card` class (alongside `.publication` or `.action`/`.filter`) that holds their common metrics — padding, radius, cursor, hover — and every card titles itself with `.card-title` (the publication's is an `<h2>`, the action card's a `<span>`), styled by one shared rule for size/margin, including the title's `display: inline-block`, which is load-bearing (an inline-block's top margin does not collapse with the meta line's bottom margin, so a `display: block` title would sit at half the gap). `styles-base.css` sets the sub-row type on `.authors, .card-text` together, and `.card-media` is the one wrapper class for both media slots (a publication's `<img>` thumbnail or an action/filter's inlined SVG miniature), framed by a single rule — the thumbnail's loading tint being the only difference. Every card title is bold now (`.card-title`'s own `font-weight`); the only per-kind declaration left is the action/filter tile's hairline — an inset `box-shadow` rather than a real border, since a border eats 1px of content width per side that a plain publication card keeps, which would sit the two kinds on slightly different inner grids. Both kinds render through `_includes/card-action.html` as a **plain gallery card** normally with no image — an optional `media="<include>.svg"` param renders one into a `.card-media` slot above the text (the `view:network` card and every research-cluster card use it, for their generated graph miniatures; see **Network view**): a two-line `.card-meta` (a literal year or a `year: now` → build year, then ` · {{ eyebrow }}`, then an optional italic `.venue` second line via `<br>`) plus a `.card-title`, with the standard `--tint-hover` gray on hover (a `mousedown` `preventDefault` on the `.action`/`.filter` buttons stops a click from starting a stray text selection over the publications behind it). Clicking a cluster card sets `activeCluster` (a Set of member slugs); the three content filters — free-text (`?q=`), `activeType` (`?type=`), `activeCluster` (`?cluster=`) — are mutually exclusive and all run through the same `applySearch` pipeline (gallery hides non-matches, network fades them), shareable in the URL and cleared by Escape or the active view button. Special cards show in **gallery view only** (hidden in network via CSS) and hide whenever a filter is active; unpinned actions render at the top of `#publications`, a `pin: first` card leads the flow, and cluster cards sit inline before their span-midpoint anchor (with a `view:network` card leading the dated flow just after the forthcoming works). Masonry packs them via a combined `tiles` NodeList (`:scope > .card`, the base class shared by every tile) while count/search stay on `.publication`. Publications render in one ordered loop, year-descending then title-ascending (Forthcoming first), so the `_card_i` priority counter stays correct.
- `_layouts/publication.html` — individual publication pages. Generates a formatted Chicago author-date reference in a hidden `<pre>` (via `citation-block.html`) and copies it to the clipboard on "Cite" button click. Prev/next navigation reads the `prev_pub`/`next_pub` refs precomputed by `_plugins/ordered_publications.rb` (via `publication-nav.html`), so no page scans the whole collection in Liquid. Uses `_includes/byline-full.html` (the full citation, not the homepage shorthand; it includes `byline-text.html`, the same byline formatter `publication.html`'s `<title>` tag uses directly, capped to a single name there). Above the footer nav it renders a **"Related publications"** list — the page's three closest works, read from its node's `related` array in `site.data.network` (matched by `url`); a non-English suggestion carries a small language tag. See **Network view** for how `related` is computed (and note it works for **every** language, unlike the English-only graph).

**Motion** on the homepage is CSS, not a library — there is no animation dependency, and `js/` still holds only D3. Two distinct mechanisms, for two distinct jobs:
- **A view switch** (gallery ↔ network) and **any filter change while the network is open** go through `withCrossfade` — `document.startViewTransition` with the browser's default cross-fade. The two views share nothing on screen, so there is nothing to match up and a page-level dissolve is the whole effect.
- **A filter change within the gallery** (`withTileTransition`) animates the real elements instead, and deliberately does **not** use a view transition. A view transition replaces the live page with rasterised snapshots for its duration, so a tile in flight is a *picture* of a card, cross-fading against the page's own snapshot — which is how a large photograph could drop out of its tile mid-slide. The masonry already positions every tile absolutely and moves it with a transform of its own, so the destination is a transform we write ourselves and the browser can interpolate it directly. Three behaviours: a tile in both states **slides** to its new slot; a tile that **leaves** is cut (which suits a filter); a tile that **arrives** is pinned at its new slot with the transition suppressed (class `entering` — it still carries the transform of wherever it last sat) and fades in from there. The transition is armed only while a change is in flight, via `.animating` on `#publications`: the first layout and every resize pass write transforms too, and those must stay instant. `layoutMasonry()` runs synchronously inside the change and cancels any pending scheduled pass, so the tiles get one destination rather than a second one written a frame into the movement. Typing is debounced by `SEARCH_SETTLE` (180 ms) so a burst of keystrokes animates once rather than restarting the tiles on every character, and `prefers-reduced-motion` falls through to instant filtering in both the CSS and the JS.

The tile transform eases on a **sampled spring** — a CSS `linear()` easing generated by `scripts/spring-easing.js` (see **Commands**). This is the same curve a JS animation library computes at runtime; measuring it once and writing it down keeps the spring feel at no weight. The tiles use an **underdamped** spring (damping 0.75, 2.8% overshoot) so a tile travels a hair past its slot and settles back. The `linear()` declaration is preceded by an equivalent `cubic-bezier` one — a browser without `linear()` drops the whole shorthand, so the bezier stands as the fallback rather than leaving the property with no transition at all. (This is also why the curve is written out literally rather than held in a custom property: a `var()` that fails at computed-value time discards the earlier declaration instead of falling back to it.) Homepage thumbnails are **warmed** after first idle (still-`lazy` images promoted to `eager`), so a card revealed by clearing a filter is not an empty frame.

The homepage no longer scrolls the page for the reader: switching view or changing a filter animates/fades the tiles in place and leaves the scroll position where it was (the old `scrollToTop` jump to the filter bar is gone).

**Bio** text lives in `README.md`, split into three paragraphs with `<!-- split -->` comments. `_plugins/readme_content.rb` reads it at each build cycle and exposes it as `site.data.readme_content` for the `home` layout. This way `README.md` doubles as the GitHub repo readme. The bio is currently **always visible**: the old show/hide toggle (its JS, the `bioVisible` localStorage state, and the `grid-template-rows` collapse animation) was stripped out and is being rebuilt from scratch — `.bio-shell` is now a plain wrapper carrying the header's bottom spacing, and the `.bio-toggle` button is still in the DOM but inert.

**Images** all live under `images/`, on one rule: **every source image belongs to its publication**, in `images/<publication-slug>/` — the numbered `fig_00N.webp` figures, plus an optional `cover.webp` for the card/social image when it is not one of those figures (either because a purpose-made image is wanted, or because the entry has no article figures at all — a book cover, a map, a magazine spread). The one exception is `images/@cards/`, which is **wholly generated**: one flat max-800px copy per publication, named `<slug>.webp` after the .md filename, written by `scripts/generate-thumbnails.py` from whatever that publication's `thumb` points at (always re-encoded at card quality, committed to the repo — rerun it after adding or changing a card image). `@cards/` is safe to delete and rebuild, is the **only** image set the homepage loads, and is never a source: `og:image` keeps pointing at the full-size original in the publication's own folder, so a social preview never inherits the gallery downsize. All source WebPs are stored at libwebp's **method 6** (max compression effort — a quality-neutral setting that just packs the same pixels tighter; see the `-m` note below): run `python3 scripts/optimize-images.py` after adding new images to re-encode every WebP under `images/` (except `@cards/`, which its own generator already writes at method 6, and `@icons/`) at method 6 to a strict visually-lossless PSNR target, keeping the result only when it is meaningfully smaller — so no image is ever degraded or enlarged, and the pass is idempotent. Use `--dry-run` to preview savings. (`method` is cwebp's effort dial `-m` 0–6; it does **not** change quality, so a higher method means a smaller file at the same fidelity — most gains come from figures originally saved with the fast default.) **There is one image field, `thumb`** — a path under `images/`, always inside the publication's own folder: a body figure like `<slug>/fig_002.webp` when the card should show a figure from the article, or `<slug>/cover.webp` when it should not. It is the source for the generated homepage card **and** the OG/Twitter/JSON-LD social image (`_social_img = thumb`), so the shared preview always matches the card. There is **no on-page hero**: every publication's on-page imagery comes from body figures (`{% include figure-single.html %}`). Entries whose "content" is really a single image — a book cover, a map, a magazine spread — open the body with a **caption-less lead figure** pointing at that image (the same `<slug>/cover.webp` the `thumb` uses). A `cover.webp` is *not* automatically displayed, though: three entries carry one purely as a social preview and show nothing on the page, which is why they declare no images in the sitemap. Because a `thumb` can have any aspect ratio, the homepage card reserves space from the **thumbnail's own** intrinsic size (read at build time via the `image_size` filter); the author portrait sits directly in `images/` (full-size `Dario-Rodighiero.webp` for OG cards/JSON-LD, downsized `Dario-Rodighiero-640.webp` for the homepage header); `images/@icons/` holds the site icon set — `favicon.ico` (legacy tab icon, ~5 KB), the vector `icon.svg` (modern browsers), `apple-touch-icon.png` (180px, iOS/Android home screen), and `icon-192.png` / `icon-512.png` referenced by the root `site.webmanifest`. All are derived from one orthographic graticule-sphere source on a white background; both layouts declare them in `<head>` (SVG preferred, `.ico` as fallback) plus `<link rel="manifest">`. The `@` prefix sorts those folders first in listings; an underscore would not work, since Jekyll excludes underscore-prefixed paths from the build. OG/Twitter cards and JSON-LD use `/images/{{ thumb }}` (with `og:image:width`/`height` read from that image via `image_size`); homepage cards use `/images/@cards/{{ slug }}.webp`.

**Fonts** are self-hosted under `fonts/` (Nunito). **JS** dependencies are self-hosted under `js/` (only D3 v7 today, loaded lazily by the network view). No CDN dependencies.

**Network view** is a publication similarity graph rendered with D3 from `js/d3.v7.min.js` (lazy-loaded on first open). Everything it needs — similarity **and the layout itself** — is pre-computed offline by `scripts/build-network.py`, which: (i) parses Markdown abstracts and strips footnotes, bibliographies, headings, links, inline code, HTML and Liquid tags, blockquote markers, bold/italic emphasis, and every parenthetical aside (citations, figure references, acronyms) together with any leftover list markers; (ii) embeds title + full text with `Alibaba-NLP/gte-base-en-v1.5` (768-dim, 8192-token window via `MAX_SEQ_LENGTH`, long enough that full-text articles are embedded whole rather than truncated) — **English originals natively, non-English originals via machine translation into the same space** (opus-mt; see the per-page suggestions section for details), so every original work has a comparable vector; a **translation** is not embedded (it borrows its source's vector and is attached by the dashed forced edge below); (iii) computes pairwise cosine similarity among all originals; (iv) attaches each translation as a regular node joined **only** to its original by a forced edge — drawn dashed on the page — rather than linked by similarity; (v) shells out to **`scripts/layout-network.js`** (Node + the vendored d3) to bake the force-directed arrangement over all nodes; and (vi) writes `_data/network.json` (committed) — the node list (slug, title, url, index, **baked `x`/`y`**), the **`links`** array (**mutual k-nearest-neighbour** over all originals: a pair (of any language) is linked only when each ranks the other within its top `MUTUAL_K = 2` most-similar neighbours *and* the similarity clears `STRONG_SIM = 0.65` — so every similarity edge is reciprocal and a node may carry several edges; a node whose top picks never reciprocate is then given a single **nearest-neighbour fallback** edge to its strongest match above `FALLBACK_SIM = 0.60` (kept below `STRONG_SIM` so these rescue links form a distinct weaker tier) — flagged `fb` in the link and drawn at reduced opacity on the page, since it is one-directional and weaker than the reciprocal backbone — but a node similar to nothing, or already attached via a translation edge, is left unconnected), the **`canvas`** size the positions were baked into, and a per-node **`related`** array (the three closest works — the single "three closest" list, shared by the publication pages and the network selection panel; see below). The internal similarity matrix is used only at build time (for the mutual-KNN links and the layout) and is deliberately **not** written to `network.json`. It also writes a **`clusters`** array driving the homepage's **auto research-cluster filter cards** (see **Special cards**). A cluster **qualifies** on the mutual backbone alone — a connected component of the strong reciprocal (+ forced translation) edges with the fallback `fb` edges dropped, holding at least `MIN_CLUSTER_SIZE` (3) **original** works (translations never count toward the size, nor help connect originals). Once it qualifies, its **membership** is broadened along the fallback edges — and the translations of its members — so the card's `slugs` also select those weakly-attached/translated works (a fallback edge is followed only when it doesn't merge two separate qualifying clusters). Each cluster is auto-labeled by TF-IDF over its members' cleaned text (unigrams + a recurring bigram when both its words are top terms; English/French/Italian stopwords filtered). `build-network.py` emits only the **structural** cluster fields `{id, label, terms, slugs, year_start, year_end, span, size, anchor_slug}` (where `size` counts original works and `anchor_slug` is the gallery publication the card renders just before — the first work at or below the cluster's **span midpoint**); the card **text** is added by a separate model-free pass, **`scripts/build-cards.py`**, which reads/rewrites the same `network.json` and, keyed on each cluster's auto `label`, layers the hand-written entries of one `CLUSTER_CARDS` table (grounded in the mutual core's abstracts): a short `title` (the subject, as a name), a two-sentence `description` (what the work does to it, then why it matters), and an optional `filter` — the chip shown in the search box, emitted as `filter_label` and defaulting to the title. A cluster with no entry falls back to its auto `label` plus a description generated from its own TF-IDF terms, so a new cluster is never a blank card. A full `build-network.py` run invokes `build-cards.py` automatically at the end, so the two stay in sync; rewording a card alone is a fast `python3 scripts/build-cards.py` with no embedding model in the loop. The same run also writes the homepage cards' **miniatures of the graph** (committed): **`_includes/network-preview.svg`** for the `view:network` card and one **`_includes/network-cluster-<id>.svg`** per research cluster, all drawn by `write_preview_svgs()` from the very same baked coordinates, so a card can never show a different map than the view behind it. A cluster miniature is the **whole map in the shared frame** — its own members and the links between them at full ink, everything else wrapped in one group at `PREVIEW_DIM_OPACITY` (`0.3`, the live view's `.filtered-out`) — so the five cards read as small multiples of a single map and each tile is a picture of both where its cluster sits in the body of work and what clicking it does. The frame (`_preview_frame()`) is always computed over **all** nodes, which is what keeps the tiles registered with each other; stale `network-cluster-*.svg` files are deleted on each run, so a cluster that disappears leaves no orphan include. It is a **true reduction**, not a redrawing: the `PREVIEW_*` constants are the live view's own values (link stroke `0.5`, marker `r3`, dashed `0.9`/`3 2.5` translation edge, `0.3` fallback opacity), so shrinking the canvas to card width thins the lines exactly as scaling the real graph down would. The ground is transparent and the ink is `currentColor` (`PREVIEW_INK`), with markers filled `var(--bg)` (`PREVIEW_NODE_FILL`) so links never show through them: the graph inherits the page, drawn black on white by day and **in negative** — white on the dark surface — once the night toggle flips `--fg`. That is exactly why they live in `_includes/` (not `images/`) and are **inlined** through the card's `media` slot: an `<img>` is an isolated document that can see neither `currentColor` nor the site's manual toggle, so it would stay black-on-white in night mode. Inlining also avoids a second request and any CLS handling. The viewBox is framed on the node **barycentre** rather than on the bounding box — each axis extends symmetrically to whichever side reaches further (plus `PREVIEW_MARGIN`) — so the centre of mass lands in the exact middle of the tile instead of the map sitting visually off to one side. So adding a publication regroups the cards with no manual tagging. `build_clusters()` needs each publication's `year` (now parsed in `parse_pub`). A non-English **original** now participates in the similarity graph like any English one (embedded via machine translation), so it carries measured edges — e.g. *Méduse* ↔ *The Trajectories Tool* (0.91); a very strong cross-language pair can pull both nodes into their own small component, which is in keeping with this graph's many small clusters. Only **translations** are excluded from the similarity search: a human translation of an English original (`translation_of` in its front matter) carries the forced dashed edge to its source described above. Every node's **selection panel** lists "three closest" from that same `related` array — the identical list its publication page shows — so the graph and the pages never disagree.

**Per-page "related" suggestions** are a **separate** ranking of the same embeddings, layered on the same file for the publication pages. Each node also gets a **`related`** array — its `RELATED_K = 3` closest publications by cosine similarity in the English embedding space — the single "three closest" list, consumed by both `publication.html` and the network selection panel (so the two never disagree). To place a non-English publication in that space, `build-network.py` **machine-translates** it to English: a non-English **original** (not itself a translation) is translated with a small offline opus-mt model (`Helsinki-NLP/opus-mt-fr-en` / `opus-mt-it-en`, chosen per `lang` from `OPUS_MODELS`; sentence-chunked to the model's window, deterministic beam search) and embedded like any English document; a **translation** simply borrows its source's vector (same work, no MT needed). **Every publication is a candidate, translations included** — only the page itself is excluded — so a translated work's page leads with the same work in the other language at ~1.00 (e.g. *The Analogous City, the Map* → *La Città Analoga, la Mappa*, tagged), and cross-language suggestions surface naturally. Each **work** appears at most once, though: a translation shares its source's vector, so the two tie and the tie breaks toward the original (a translation only fills a slot when its work isn't already listed), which keeps the same work from taking two of the three slots. How this relates to the graph: the same original vectors also build the internal similarity matrix behind the mutual-KNN edges (a non-English original is a first-class similarity node — see above), but that matrix lives only at build time and is not shipped; the browser reads `related` alone. Machine translations are held in a gitignored `scripts/.translation-cache.json` (keyed by model + source text, like the embedding cache), so only originals whose text changed are re-translated; add a language to `OPUS_MODELS` if a new source language appears. `layout-network.js` is the single source of truth for the graph geometry — it owns the link rule (`MUTUAL_K`, `STRONG_SIM`, `FALLBACK_SIM`), the force constants (`NODE_SPACING`, `CHARGE_STRENGTH`, `GRAVITY`, `LINK_DIST_BASE`/`LINK_DIST_SPAN`, `CHARGE_DISTANCE_MAX`, `LAYOUT_SEED`, `LAYOUT_TICKS`), the component-anchoring strategy (`ANCHOR`: `center` — all nodes share one gravity well, so clusters settle as islands and unconnected nodes fill the gaps — or `ring` — largest component centred with the rest pinned on a perimeter ring, which suits one dominant hub but scatters this many-small-components graph into a halo), and the `CANVAS_W`/`CANVAS_H` it lays out into. Note collide spacing (`NODE_SPACING`) governs marker/click separation only, not label legibility: labels render on hover, one at a time. The page consumes the data via Liquid and only **fit-scales** the baked positions into the live stage (uniform scale + center, fixed-px markers/labels; re-fit on resize) and draws the baked links — no force simulation runs in the browser. Re-run `KMP_DUPLICATE_LIB_OK=TRUE python3 scripts/build-network.py` after editing publications (it needs Node on PATH for the layout step).

**Plugins**: `jekyll-feed` (RSS for the `publications` collection), plus ten local plugins in `_plugins/`:
- `autolink_urls.rb` — Liquid filter that wraps bare `http(s)://` URLs in anchors when rendering full-text bodies (skips URLs already inside `<a>` tags)
- `decode_numeric_entities.rb` — Liquid filter turning numeric character references (`&#8217;` / `&#x2019;`) into UTF-8 characters; applied to publication excerpts before `escape_once`, which would double-escape hex entities
- `front_matter_validator.rb` — a high-priority generator that checks every publication's front matter (required fields, valid `type`, referenced images exist, ISSN format) and logs warnings/errors at build time, so bad metadata is caught before deploy
- `git_mtime.rb` — adds `git_mtime` (last commit date) to each publication and `site.data` for sitemap `lastmod`; needs full git history (the deploy workflow uses `fetch-depth: 0`)
- `image_size.rb` — Liquid filter returning a WebP's intrinsic pixel dimensions (pure-Ruby parser), used by `_includes/figure-single.html` to set `width`/`height` and avoid CLS
- `ordered_publications.rb` — a `post_read` hook holding the site's canonical publication order (Forthcoming first, then year descending, title ascending within a year) in exactly one place: it exposes `site.data.ordered_publications` for the gallery flow and gives each document a `prev_pub`/`next_pub` hash (url + title only, so the pages don't reference each other through page data) for `publication-nav.html`. `publication_date.rb` reuses the same sort key
- `publication_date.rb` — derives `page.date` from `year` so the RSS feed preserves the homepage sort order
- `publication_figures.rb` — a high-priority generator collecting the images that actually appear **inside** a publication's body — the `figure-single.html` / `figure-group.html` includes, scanned off the raw `doc.content` — as `figures`, a list of site-absolute paths. This is what `sitemap.xml` declares per publication (see **SEO**), rather than the `thumb`. The two includes pass paths differently (figure-single an absolute `src="/images/…"`, figure-group a pipe-delimited `images="slug/a.webp|…"` it prefixes itself), so both are normalised, then deduplicated per document. Anything under `images/@cards/` is dropped — those are gallery/social crops, not article content, including where an abstract-only entry opens on its own card image — and a path missing from disk is skipped with a warning, since a 404 in an image sitemap is a crawl error rather than a discovery
- `readme_content.rb` — exposes `README.md` as `site.data.readme_content` (see Bio above)
- `redirect_pages.rb` — URL **aliases**: any page or publication may list `redirect_from` in its front matter (a string or a list of site-absolute paths, e.g. `/surprise-machines`) and the plugin emits a small redirect stub for each — `noindex`, absolute `rel=canonical` on the real page, `<meta refresh>` + `location.replace` to it. An alias without an extension is written as `<alias>.html` (served extensionless by GitHub Pages and `jekyll serve`); one ending in `/` becomes `<alias>/index.html`. Duplicate or non-slash-prefixed aliases are skipped with a build warning. Stubs stay out of `sitemap.xml`, which loops `site.publications` only. This is a local replacement for the removed `jekyll-redirect-from` gem, so no new dependency

**Continuous integration** is two GitHub Actions workflows in `.github/workflows/`:
- `deploy.yml` — builds and publishes the site on every push (GitHub Actions deployment, not branch deployment, so the local `_plugins/` run at all). It checks out with `fetch-depth: 0` because `git_mtime.rb` needs full history, and deletes the parked `/feed/posts.xml` that `jekyll-feed` always emits alongside the real `/feed.xml`
- `links.yml` — a weekly (Monday 09:00 UTC) **lychee** crawl of the built `_site/`, plus `workflow_dispatch` for a run on demand. It accepts `200,202,206,302,403,429,999` — a bare 403 or 429 is a bot wall, not rot — and carries a hand-maintained `--exclude` list of hosts that block crawlers outright (`doi.org` is excluded because publisher landing pages behind a DOI answer inconsistently, so a resolving DOI still reports as broken). On failure, **`scripts/link-context.py`** turns lychee's flat `lychee/out.md` list into a report that says *where* each dead URL lives: the full citation when the URL sits in a Markdown bullet, the surrounding paragraph when it is inline prose, the publication title when it is in front matter. That context is what makes the report actionable — a bare list of URLs does not say which reference to go fix. Because a link can rot without anything in the repo changing, the run is scheduled rather than push-triggered, and a red result is normal maintenance rather than a broken build

**Dead references get an archive fallback rather than a deletion.** When a cited URL stops resolving, the original stays exactly where it is — it is what the publication cited, and rewriting it would falsify the citation — and a Wayback link is appended in parentheses: `<original URL> ([archived](https://web.archive.org/web/<timestamp>/<original URL>))`. Pick a capture contemporaneous with the reference's own access date, not merely the most recent one: a late snapshot of an expired domain can be a parking page, and archive.org will happily serve it. Verify a candidate through `https://archive.org/wayback/available?url=…&timestamp=…`, whose `closest` object reports the `status` the crawler actually recorded — only a `200` capture is worth linking. The label follows the language of the piece (`archiviato` in the Italian entries), since it is prose inside a bibliography, not UI. A URL with no usable capture is left alone: a fabricated or wrong-content archive link is worse than an honest dead one

## SEO

Both layouts share a common `<head>` structure:
- `<title>`, `meta description`, `meta keywords`, `rel=canonical`, `robots: index, follow, max-image-preview:large, max-snippet:-1, max-video-preview:-1` (indexing was never blocked; the preview directives only lift the caps on how a result may render in Search and Discover)
- Open Graph (`og:title`, `og:description`, `og:url`, `og:type`, `og:image`, `og:image:alt`, `og:locale`)
- Twitter Card (`twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`, `twitter:image:alt`)
- JSON-LD structured data

**`sitemap.xml`** carries the Google image extension (`sitemap-image/1.1`): the homepage declares the portrait, and each publication declares its `figures` (from `publication_figures.rb` — what the page actually shows, including a displayed `cover.webp`; the generated `@cards/` copies are excluded). Only `image:loc` is emitted; `image:title`, `caption`, `license` and `geo_location` were discontinued in August 2022 and are ignored. `changefreq` and `priority` are likewise gone — Google stopped reading them in 2023, so each `<url>` carries just `loc`, `lastmod`, and its images. Note the excluded card images are not deindexed by their absence — they stay on the page as lead figures and as `og:image`; blocking them would take a `robots.txt` disallow, which social crawlers honour too and would strip the preview image from those entries.

**Translation sets** (`translation_of` in a translation's front matter) are resolved once per page into `_origin` (the original — this page, or the source it translates) and `_siblings` (every translation of that original, this page included when it is one), so the tags below hold for any number of language versions, not just a pair. Each page emits reciprocal `hreflang` alternates covering origin + siblings — a set that always contains the page itself, supplying the required self-reference — with `x-default` on the original; `og:locale:alternate` for the same set minus itself; and JSON-LD `translationOfWork` (the origin) / `workTranslation` (the sibling translations), each nested node carrying its own `@type` from `publication_types.yml`. Publication pages also surface the bibliographic front matter to Google Scholar (`citation_volume`, `citation_issue`, `citation_firstpage`/`citation_lastpage` split from `pages`, `citation_publisher`) and as JSON-LD `pagination`. Scholar reads the page tags as literal numbers, so a Chicago-condensed range (`pages: "301–9"`) is expanded back to a full `citation_lastpage` (`309`) by borrowing the missing leading digits from the first page — the visible citation keeps the condensed form. `DC.publisher` is the front-matter `publisher` when present, falling back to `Dario Rodighiero` for self-published pages.

**Zotero import** reads the same tags through its Embedded Metadata translator, which resolves the item type from the HighWire venue tag first (`citation_journal_title` → journalArticle, `citation_conference_title` → conferencePaper, `citation_book_title` → bookSection) and only falls back to `DC.type` when none is present. That fallback is why `_data/publication_types.yml` prefers a `dc` value Zotero maps firmly over a broader DCMI term: `map` (→ map) rather than `image`, which Zotero can only guess at as artwork. `book` and `interview` already match Zotero item types by name. One known imprecision is left in place: a `magazine` piece carries `citation_journal_title` so Scholar and readers still get the venue, which pins it to journalArticle rather than magazineArticle.

**`og:locale`** is set to `en_US` by default; publications with `lang: it` in their front matter get `it_IT`, and `lang: fr` gets `fr_FR`. The same `lang` (defaulting to `en`) also drives the publication page's `<html lang>`, the `citation_language` / `DC.language` meta tags, and JSON-LD `inLanguage`, so each page declares its real language end-to-end. The homepage stays `en` (English UI/bio); there is no translated UI or per-language page tree.

**OG/Twitter image**: `home.html` always uses the author portrait (`images/Dario-Rodighiero.webp`). `publication.html` uses `page.thumb`, falling back to the same portrait so social cards are never blank.

**JSON-LD types** on publication pages follow Schema.org: `Book`, `ScholarlyArticle` (journals, conferences, book chapters), `Article` (magazine pieces — not peer-reviewed scholarly venues, so they get the more general type), and `Map`. `home.html` emits a `WebSite` + `ProfilePage` + `Person` graph with `sameAs` links to ORCID, Google Scholar, GitHub, LinkedIn, and Zotero.

Three things tie that graph together and keep the citation modelled the way a scholarly consumer expects:
- **One author identity.** Every name in the byline renders through `_includes/jsonld-person.html`, which gives Dario's node `"@id": "https://orcid.org/0000-0002-1405-7062"` — the same `@id` the homepage `Person` carries. That shared identifier is the only thing telling a crawler the author of sixty-odd publication pages and the subject of the homepage are one entity; without it each page declares an unrelated person who happens to share a name. Co-authors stay bare names (no stable identifier for them). `_includes/jsonld-people.html` wraps it to emit a whole person-valued property from an " and "-joined field, and **every byline role goes through it**, not just `author`: `editor` and `translator` are real CreativeWork properties, while `interviewer` and `preface` have no Schema.org equivalent and fold into the general `contributor`. That is what keeps Dario in the graph of works he did not author — the interviews (cited under the interviewee) and the two *Analogous City* maps (authored by Rossi et al.) reach him as `contributor` and `editor` respectively, so no publication where he appears in any role leaves him out.
- **Container vs. publisher.** `venue` means different things per type, so `publication_types.yml` carries a `container` key saying how to model it: `periodical` (journal, magazine) emits `isPartOf` a `Periodical`, nested through `PublicationVolume` / `PublicationIssue` when `volume` / `issue` are known; `book` (chapter, conference) emits `isPartOf` a `Book` — the containing book or the proceedings; and **omitted** means `venue` names the press itself, so it stays `publisher`, which is right for `book` and `map` (Métis Presses, EPFL Archizoom) and for `interview`, whose venue may be an institution rather than a serial. Where `container` is set, `publisher` is emitted only from a real `publisher` field and is otherwise dropped, rather than repeating the venue as an Organization that published it.
- **Two descriptions, two budgets.** `description` must fit a search snippet, so it stays the 22-word/160-char truncation the `meta description` uses; `abstract` has no such budget and carries the abstract whole — on a full-text article the lead before `<!--more-->`, which is exactly the abstract, and on any other entry the body, which is the abstract already. The split happens *before* `strip_html`, since stripping tags takes the `<!--more-->` comment with them.

**ISSN / ISBN**: the front-matter `issn` / `isbn` emit `citation_issn` / `citation_isbn` — the identifiers Scholar and Zotero use to resolve a venue that a name alone leaves ambiguous — and reach JSON-LD by what they identify: an `issn` only ever lands on a `Periodical` node (Schema.org does not define it for `Book`), while an `isbn` lands on the `isPartOf` book where the type has a container and on the entity itself where it does not, since there the work *is* the book. Coverage is 23 `issn` and 19 `isbn`, and partial by design — a wrong identifier is worse than a missing one. They come from Crossref by DOI, from a Zotero export of Dario's own library, from the journal's own site or a library registry, or from Dario directly; every one is check-digit validated before it lands (the ISSN mod-11 and ISBN-13 mod-10 rules catch a transcription slip, which is the realistic failure here), and a venue where none could be confirmed carries no field. ISBNs are stored unhyphenated, since hyphenating one correctly needs the registrant-range tables and a wrong split is worse than none.

**Freshness**: `git_mtime` (the file's last commit date, computed in `_plugins/git_mtime.rb` for sitemap `lastmod`) also feeds `article:modified_time` and JSON-LD `dateModified` on every publication page. Its no-git fallback only accepts a four-digit `year`; `year: Forthcoming` falls through to today, since `Forthcoming-01-01` would be an invalid date in both the sitemap and the structured data.

**`404.html`** is `noindex` and deliberately carries **no** `rel=canonical` — pointing one at the homepage would ask a crawler to consolidate every missing URL into it.
