# Motion

Motion on the homepage is CSS, not a library — there is no animation dependency, and no
rendering one either: `js/` holds only the analytics snippet. Two distinct mechanisms, for
two distinct jobs.

## 1. View switch — `withCrossfade`

A view switch (gallery ↔ network) and **any filter change while the network is open** go
through `document.startViewTransition` with the browser's default cross-fade. The two views
share nothing on screen, so there is nothing to match up and a page-level dissolve is the
whole effect.

## 2. Filter change within the gallery — `withTileTransition`

This animates the real elements and deliberately does **not** use a view transition. A view
transition replaces the live page with rasterised snapshots for its duration, so a tile in
flight is a *picture* of a card, cross-fading against the page's own snapshot — which is how
a large photograph could drop out of its tile mid-slide. The masonry already positions every
tile absolutely and moves it with a transform of its own, so the destination is a transform
we write ourselves and the browser can interpolate it directly.

Three behaviours:

- a tile in both states **slides** to its new slot;
- a tile that **leaves** is cut (which suits a filter);
- a tile that **arrives** is pinned at its new slot with the transition suppressed (class
  `entering` — it still carries the transform of wherever it last sat) and fades in from
  there.

The transition is armed only while a change is in flight, via `.animating` on `#publications`
(`armTileMotion()` adds the class and sets the timer that takes it off again): the first
layout and the resize passes that change nothing write transforms too, and **those must stay
instant**. `layoutMasonry()` runs synchronously inside the change and cancels any pending
scheduled pass, so the tiles get one destination rather than a second one written a frame
into the movement.

Typing is debounced by `SEARCH_SETTLE` (180 ms) so a burst of keystrokes animates once rather
than restarting the tiles on every character, and `prefers-reduced-motion` falls through to
instant filtering in both the CSS and the JS.

## A change of column count is the same event

The grid re-packs and every tile gets a new slot, so `layoutMasonry()` arms the identical
class and curve when the count it lays out into differs from `lastCols` (the count of the
previous pass; `null` before the first layout and after `clearMasonry()`, since a tile with no
transform has nowhere to travel from). Nothing enters or leaves, so there is no fade beside it.

**The one-column boundary is excluded on both sides** (`cols > 1 && lastCols > 1`). From two
columns up a card is always `--card-w`, so the tiles that travel are the same tiles at the
same size and the move is the whole change. At one column the card is the page's full width —
crossing that line resizes every tile as well as moving it, and width is a layout property
that can only change instantly (animating it would reflow every card's text on every frame),
so a card changing size mid-glide reads as two unrelated things at once. The page's height
roughly doubles or halves there too, putting nearly every tile past the distance cut anyway.

## Two things are cut rather than animated

On one principle: **don't animate a move the reader cannot follow.**

**Per tile.** A slot moving further than `window.innerHeight` gets class `snapping`
(`transition: none`) for that one style change and is released after a flush. Past a screen of
travel there is nothing for the eye to follow, and a column change moves the deepest tiles in
this gallery by thousands of pixels — measured on 4 → 3 at 897px of viewport, 47 of the 68
tiles were beyond the line, all far below the fold.

**Per pass.** A change that shortens the gallery past where the reader is standing is left to
cut entirely: the browser then clamps the scroll position — 3 → 4 at the foot of the page
pulls the viewport ~2500px up — and a slide playing while the viewport is dragged the other
way reads as the page coming apart. Nothing can prevent the clamp (the page really is
shorter), so the pass gives one jump instead of a jump with movement inside it. Only a
*rising* count can clamp, since fewer columns is a taller page.

Knowing the new height before the first transform is written is why the pack runs into an
array (`slots`) and the DOM writes follow in a second loop — a transform written outside the
armed class cannot be taken back. The previous y each tile is travelling from is likewise
remembered (`placedY`, indexed alongside `tiles`) rather than parsed back out of the transform
string this same function wrote.

## The spring

The tile transform eases on a **sampled spring** — a CSS `linear()` easing generated by
`node scripts/spring-easing.js`, which prints the curves to paste into `_layouts/home.html`
and writes nothing itself, so a retune is a parameter change rather than a hand-tweaked list
of numbers. This is the same curve a JS animation library computes at runtime; measuring it
once and writing it down keeps the spring feel at no weight.

The tiles use an **underdamped** spring (damping 0.75, 2.8% overshoot) so a tile travels a
hair past its slot and settles back.

The `linear()` declaration is preceded by an equivalent `cubic-bezier` one — a browser without
`linear()` drops the whole shorthand, so the bezier stands as the fallback rather than leaving
the property with no transition at all. This is also why the curve is written out literally
rather than held in a custom property: a `var()` that fails at computed-value time discards
the earlier declaration instead of falling back to it.

Homepage thumbnails are **warmed** after first idle (still-`lazy` images promoted to `eager`),
so a card revealed by clearing a filter is not an empty frame.

## Scrolling — exactly one case

The old blanket `scrollToTop` jump to the filter bar is gone. Switching view, typing, and
changing a type or free-text filter all animate/fade the tiles in place and leave the scroll
position where it was.

The exception is **selecting a research cluster** (`scrollToResults()`), because it is the one
filter whose control is not in the bar at the top: cluster cards are interleaved at their
span's midpoint, so the click happens far down the flow while the works it selects pack at the
very top, leaving every result above where the reader is standing. (The short case needs
nothing: a filtered page that no longer fills the viewport can only clamp to 0, which the
browser does by itself.)

Three constraints keep it from becoming the old behaviour again:

- It fires **only on setting a cluster** — not clearing one, not a type or text filter — so
  the test is duplicated at the call site, ahead of the transition the cluster branch runs
  inside.
- It scrolls **only upward**, since a reader already above the gallery's first row has the
  results below them and would merely lose the masthead.
- It runs **before** the filter, not after: the gallery's top edge is fixed by the header
  above it and does not move when the tiles do, so the destination needs no layout pass, and
  going first puts the tiles' rearrangement inside the viewport the reader ends up watching.

It lands the gallery under the sticky `.filters` bar (measured, not hardcoded) rather than at
the viewport top, so the bar does not cover the first row while showing the filter's label —
the only thing on screen naming what just happened. Travel past one viewport height cuts
instead of gliding, the same rule the tiles follow, and `prefers-reduced-motion` always cuts.
